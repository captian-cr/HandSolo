# 故障排查

> 排查顺序永远是：**先看日志 → 再跑 safe-mode → 最后才改参数**。
> 顺序反了会把"摄像头掉帧"误诊成"阈值不对"，越调越乱。

---

## 0. 先拿到现场的三样东西

| 要什么 | 怎么拿 |
|---|---|
| **日志** | `logs\handmouse-YYYY-MM-DD.log`（`pythonw` 启动时全部输出都在这里） |
| **实时报错** | 双击 `HandSolo（诊断·看报错）.bat`，黑窗口里能直接看到 traceback |
| **诊断指标** | `python -m handmouse --safe-mode --diagnostic-seconds 20` |

`safe-mode` 的关键指标是 `hand_detection_rate`（检出率）：

- **> 0.9** → 视觉链路正常，问题在手势判据或输入注入；
- **0.3 ~ 0.9** → 光照 / 摄像头 / 手离得太远；
- **< 0.3** → 基本没检测到手，先解决硬件与光照。

这条分界线能省掉 80% 的瞎调。

## 1. 启动类

### 双击之后什么都没发生

`pythonw.exe` 没有控制台，任何异常都被吞进日志。看这里：

```
<项目目录>\logs\handmouse-YYYY-MM-DD.log
```

日志都开不出来（连文件都没生成）说明 Python 解释器都没起来 → 用
`HandSolo（诊断·看报错）.bat` 看真实报错。

### 弹窗说「已在运行」

单实例互斥量生效了，说明另一个实例还活着。想在两个之间切换：

1. 托盘/任务管理器里找到 `pythonw.exe` 结束掉，或
2. 用 `HandSolo（诊断·看报错）.bat` 启动一次（会打印已在运行），确认后结束它。

### 报 `AttributeError: 'NoneType' object has no attribute 'write'`

这是 `pythonw` 下 `sys.stdout is None` 的典型症状。本项目已经在
`__main__._ensure_output()` 里把输出接到日志文件，如果你在**自己写的脚本**里
遇到，需要同样处理：

```python
if sys.stdout is not None:
    sys.stdout.reconfigure(...)
```

### 报「无法打开摄像头 0，请检查占用和隐私权限」

按顺序查：

1. 会议软件（腾讯会议 / Zoom / 钉钉）、相机应用、OBS 有没有占着；
2. 设置 → 隐私和安全性 → 摄像头 → **允许桌面应用访问摄像头** 打开；
3. 换个 USB 口；外接摄像头序号可能不是 0，用 `--camera 1` 或先跑
   `python scripts\probe_camera.py`；
4. 都不行 → 打开 Windows「相机」应用，如果它也黑屏，是驱动/硬件问题，与本程序无关。

## 2. 光标类

### 光标完全不动

按概率从高到低：

| 检查 | 说明 |
|---|---|
| **是不是还没接管** | 默认启动是**暂停**的。按 `M`，或对镜头**五指张开保持约 0.8 秒**（`wake_by_open_palm`） |
| **HUD 是否显示「未进入控制态」** | `entry_gate_enabled=true` 时，必须五指张开保持 `entry_hold_ms`（默认 300ms）且**掌心朝向镜头** |
| **HUD 的 `指伸` / `指伸3D` 是否为 0** | 食指没被判成伸出。侧手角度下 2D 判据会失灵，看 `指伸3D` 更可信 |
| **手是不是出了取景框** | 指尖出框时几何不可信，程序会主动停止 |
| `hand_lost_ms` 是否太小 | 默认 200ms，低帧率下容易误判失联，可加到 300~400 |

### 光标的抖动明显 / 停在目标上还在颤

```json
"pointer_stability": 0.58,      // 调高 → 更稳、更迟钝；0.7~0.75 是常见甜蜜点
"pointer_response": 0.82,       // 调高 → 更跟手、更抖
"cursor_micro_deadband": 0.0025 // 瞄准死区；调大 → 小目标更容易停稳
```

⚠️ 但先确认**不是摄像头掉帧**：10fps 下的抖动是采样问题，调滤波只会变得更黏。

### 光标往一个方向慢慢漂

手指保持不动但光标持续移动，通常是关键点在高频抖动 + 死区太小。
先把 `cursor_micro_deadband` 从 0.0025 加到 0.004~0.006。

### 光标比手慢半拍

```json
"cursor_interpolation_ms": 42   // 调小 → 更快但更硬；16~30 更跟手
```

## 3. 点击 / 拖拽类

### 捏合点不出来

| 原因 | 处置 |
|---|---|
| `pinch_engage` 太高（捏不到位） | 从 0.42 调到 0.50~0.60。**一次只加 0.05** |
| 手在**向下**指时捏合 | `pinch_down_suppress_enabled` 会主动抑制——向下捏合时食指在几何上确实像"弯了"。改成**水平朝向**镜头再捏 |
| 手被画面边缘切掉 | 往画面中间挪一点 |
| `thumb_stop_enabled=true` 抢了停住语义 | 如果你开了"拇指张开=停住"，捏合前先把拇指收回来 |

### 一动就误触发点击

`pinch_engage` 太低。按 0.05 一档往上加，直到正常情况下误触消失。
辅助手段：`pinch_hold_ms`（默认 100ms）——只有捏合**保持**超过这么久才算点击。

### 双击变单击 / 单击变双击

```json
"double_click_window_ms": 700   // 窗口太短 → 第二下捏合赶不上；太长 → 两次单击粘成双击
"double_click_max_drift": 0.05  // 两次捏合的落点容差（归一化画面坐标）
```

### 拖拽一开始就断

```json
"drag_hold_ms": 5000            // 捏住多久升级为拖拽
"drag_gain": 1.0                // 拖拽时手的位移到光标的增益
```

拖拽期间光标锚定在掌心，靠掌心位移拖动，所以**手掌要保持在画面里**。

## 4. 手势识别类

### 双指（食指+中指）划动不触发 / 一伸食指就乱滚

判据是分层的，**有 3D 坐标时只听 3D**（`world_landmarks`），没有 3D 才退回 2D：

- 查 HUD 的 `指伸3D`：四指都为 1 说明 3D 判据在跑；
- 如果 `指伸3D` 全 0 而手明明伸着，说明**离镜头太近**（世界坐标在 0.5m 内会退化），
  往后退一点；
- 如果 HUD 显示 `指伸`（2D 关节角）与 `指伸3D` 矛盾，**以 3D 为准**——2D 那个
  在侧手角度下不可信（实测拿它当判据，只伸食指被误判成划动的比例是 52%）。

### 五指张开不触发「待机」/ 左右挥动不翻页

- 五指张开需要**确认窗**（300ms）才切待机，动作要停住；
- 挥动需要 `swipe_hold_ms`（650ms）持续位移，划一下立刻回手不算；
- 反向要先停约 `swipe_window_ms`（800ms），这是**故意**的，否则"回手"会被算成反向。

### 握拳把控制态关了，还得重新做进入姿势

```json
"fist_exits_gate": false   // 握拳只冻结本次动作，不退出控制态（推荐）
```

手放松时自然会半握，`_is_fist` 会命中。作者的实机记录里这种误退出出现过
93 次、累计 76 秒。

## 5. 磁吸 / 停留类

### 磁吸在两个小图标之间来回跳

0.9.1 已修（释放宽限期 + 窗口统一裁决）。如果你还在旧版，升级即可。
若新版仍有：把 `cursor_snap_radius_px`（默认 34）调小到 24~28。

### 停住一秒也不亮「停留」

0.9.1 重写了判据（旧版物理上不可能触发）。若仍不亮：

1. 先看 HUD 有没有 `停留 x.x/1.0s` 在涨——**涨到 1.0 才亮**；
2. 涨到一半被清零 = 手还在动（阈值 `pinch_pre_dwell_epsilon` 默认 0.030 ≈ 57px）；
3. 想更快触发就把 `pinch_pre_dwell_ms` 从 1000 降到 600~800。

### 停留时光标冻住了，但我只是想歇一下

```json
"pinch_pre_dwell_freeze": false   // 停留只开磁吸窗口，不冻结光标
```

## 6. 性能类

### 帧率低、感觉卡

按这个顺序查，**别跳步**：

**① 先看是 capture 低还是 inference 低**

`--diagnostic-seconds` 的两个数是两个不同的瓶颈：

| 现象 | 含义 |
|---|---|
| `capture_fps` 只有 10 左右 | 摄像头/采集后端的问题（见 ②） |
| `capture_fps` 正常但 `inference_fps` 只有 8 | **多半是还在暂停态**（见 ③） |
| 两个都正常但看着卡 | 上层开销：HUD 绘制 / UIA 磁吸 / 窗口球 |

**② `capture_fps` 只有 10 → 换采集后端**

`config.json` 里 `camera_backend`：`"dshow"` ↔ `"msmf"`，重启。

实测（2026-10-25，每只摄像头单独重开进程测）：

| 摄像头 | dshow | msmf |
|---|---|---|
| 笔记本内置（ID 0） | 10.0 fps | **29.9 fps** |
| 外置 USB（ID 1，上限 640×480） | **10.0 fps（锁死）** | **29.8~30.4 fps** |

外置摄像头在 dshow 下换到 320×240 / 160×120 **同样是 10.0fps**，所以不是带宽问题，
是这条路径下的自动曝光把单帧曝光时间拉到了 1/10 秒。而这台摄像头的
`EXPOSURE` / `AUTO_EXPOSURE` / `GAIN` 在 OpenCV 里 `set()` 全返回 False，
**没有第三种办法**，只能换后端。

**③ `inference_fps` 只有 8 → 你可能还在暂停态（正常）**

暂停时推理**故意限流到 10Hz**（省 CPU，一帧 100ms）：

```python
if self.paused_provider() and packet.captured_ns - last_paused_submit_ns < 100_000_000:
    continue
```

| 状态 | capture_fps | inference_fps |
|---|---|---|
| 暂停（默认启动态） | 30.0 | **7~8**（限流 10Hz） |
| 接管后 | 30.0 | **30.2** |

所以看到 `capture=30 / inference=8` 不是故障。想测真实推理能力必须加 `--auto-control`：

```bat
python -m handmouse --safe-mode --auto-control --diagnostic-seconds 10
```

**④ 以上都正常，还是觉得卡 → 是上层开销**

HUD 上显示的 fps **不是摄像头也不是 MediaPipe 的限制**：

| 环节 | 实测（作者的 640×480 机器） |
|---|---|
| 采集 + 推理端到端 | **29.8 fps** |
| HUD 显示 | 15 fps 左右 |

差距在上层：HUD 绘制、UIA 磁吸查询、窗口球（`window_ball_enabled`）。
想省 CPU 就关预览，**三种方式都行**：

- 启动前：`python -m handmouse --no-preview`，或双击 `HandSolo（后台无预览）.bat`；
- 运行中：窗口里按 **`P`**，或全局按 **`Ctrl+Alt+P`**（实测关掉后 30fps、CPU 0.7%）；
- 关掉之后再打开：**只能 `Ctrl+Alt+P`** —— 窗口没了，窗口里的键跟着失效；
  状态改看光标旁的小圆环（颜色含义见 README「状态圆环的颜色」）。

**⑤ 暗光也会降帧**：自动曝光在暗处会拉长曝光时间，帧率掉、画面还拖影。
把灯打开往往比调任何参数都有效。

### 程序正常运行，但画面全黑 / 一直检不到手

**多半是摄像头序号指到了虚拟摄像头**（OBS Virtual Camera、ManyCam 之类）。
它们在 DSHOW 下也能"打开成功"、也能返回 640×480，只是内容全黑——不报错，
看起来像程序坏了。判别方法：跑 `python scripts\probe_camera.py --index N`，
看 `实际画面` 后面的**亮度**；虚拟摄像头未推流时亮度是 0。

处置：把 `camera_index` 改成真实摄像头的序号。作者机器上实测的分布是
`0` = 内置、`1` = 外置 USB、`2` = 虚拟摄像头。

### 内存持续上涨

检查 `usage_log_enabled` 是否被打开（默认关）。日志/采集数据都在
`gesture_data\`，长期跑建议定期清理。

## 8. 还是不行怎么办

提 issue 时请附上：

1. `python scripts\probe_camera.py` 的完整输出；
2. `python -m handmouse --safe-mode --diagnostic-seconds 20` 的指标行；
3. `logs\handmouse-<当天>.log` 的最后 50 行；
4. 你的 `config.json`（**只贴键值，不含任何个人信息**）；
5. 说清症状复现步骤，例如"食指朝下时捏合不触发，横向朝向正常"。

第 5 条往往比前四条更有用 —— **能稳定复现的描述比一堆参数值值钱**。

### 刚启动时画面发白（一两秒后自己好）

**这是正常的，不是过曝故障。** 自动曝光在摄像头打开后会先大幅摆动再收敛。
实测同一只摄像头、同一场景：

| 打开后多久 | 画面亮度 |
|---|---|
| 0.5 秒内 | **243（近乎全白）** |
| 预热 2 秒后 | **77~97** |

所以看到预览窗刚出来那一下发白，**等两秒**。如果两秒后还白，才算真过曝 ——
那就换采集后端（`camera_backend` 换成另一个，见上一节 ②）。

`probe_camera.py` 输出的亮度是预热后测的，可以直接当结论。

### 画面发虚 / 整体朦胧、亮处有光晕

**先分清是软件还是硬件。** 有个很硬的判别方法：**换后端、换分辨率，看虚不虚**。

| 试验 | 结果 | 结论 |
|---|---|---|
| dshow 和 msmf **一样虚** | 与采集路径无关 | 不是软件 |
| 640×480 和 320×240 **一样虚** | 与分辨率/插值无关 | 不是缩放 |
| 同一房间同一距离，内置清楚、外置朦胧 | 差异在镜头 | **光学问题** |

作者的实测（同一房间、同一距离、预热 2 秒后）：

| | 清晰度指标(Laplacian 方差) | 观感 |
|---|---|---|
| 笔记本内置 | **113** | 门框、开关面板、衣柜花纹都清楚 |
| 外置 USB | **83~90** | 整体朦胧，亮处有光晕 |

外置摄像头常见的三个物理原因，按概率排：

1. **镜头保护膜没撕**（新摄像头几乎都有，观感就是"朦胧 + 光晕"）；
2. **镜头有指纹/灰**，用眼镜布擦；
3. **定焦镜头跑焦**——不少廉价摄像头镜头筒可以拧（对焦环），对着 40~50cm 处的手拧到最清晰。

先在 Windows「相机」应用里看一眼：如果那里同样糊，就与程序无关。

> 模糊会直接拉低关键点精度（抖动变大、捏合比噪声变大），所以**这一项值得较真**。
> 如果外置怎么调都糊，用回内置摄像头也是合理选择——代价是画面暗一些（实测亮度 81 vs 147）。

### 程序正常运行，但画面全黑 / 一直检不到手

**多半是摄像头序号指到了虚拟摄像头**（OBS Virtual Camera、ManyCam 之类）。
它们在 DSHOW 下也能"打开成功"、也能返回 640×480，只是内容全黑——不报错，
看起来像程序坏了。判别方法：跑 `python scripts\probe_camera.py --index N`，
看 `实际画面` 后面的**亮度**；虚拟摄像头未推流时亮度是 0。

处置：把 `camera_index` 改成真实摄像头的序号。作者机器上实测的分布是
`0` = 内置、`1` = 外置 USB、`2` = 虚拟摄像头。

### 内存持续上涨

检查 `usage_log_enabled` 是否被打开（默认关）。日志/采集数据都在
`gesture_data\`，长期跑建议定期清理。

## 8. 还是不行怎么办

提 issue 时请附上：

1. `python scripts\probe_camera.py` 的完整输出；
2. `python -m handmouse --safe-mode --diagnostic-seconds 20` 的指标行；
3. `logs\handmouse-<当天>.log` 的最后 50 行；
4. 你的 `config.json`（**只贴键值，不含任何个人信息**）；
5. 说清症状复现步骤，例如"食指朝下时捏合不触发，横向朝向正常"。

第 5 条往往比前四条更有用 —— **能稳定复现的描述比一堆参数值值钱**。

### 画面发虚 / 整体朦胧、亮处有光晕

**先分清是软件还是硬件。** 两个最常见的软件原因：

1. **MSMF 后端过曝**（实测外置摄像头：亮度 243、对比度 30，几乎全白）。
   MSMF 在 OpenCV 里**控制不了曝光**（`CAP_PROP_EXPOSURE` / `CAP_PROP_AUTO_EXPOSURE`
   全部 `set()` 返回 False、读回 -1），所以只能在 dshow 下用。
   → `camera_backend` 改回 `"dshow"`。
2. **低光照下的自动增强**：亮度低于 55 时会自动提亮 + CLAHE，极端情况下会显得"发灰"。
   这属于预期行为，把环境照亮一点即可。

**如果两个后端都虚，那是摄像头本身**。判别方法很硬：

```bat
:: 同一场景，内置与外置截帧对比
python scripts\probe_camera.py --index 0
python scripts\probe_camera.py --index 1
```

或者看日志目录里手动截的帧。作者的实测（同一房间、同一距离）：

| | 清晰度指标(Laplacian方差) | 观感 |
|---|---|---|
| 笔记本内置 | 113 | 门框、开关面板、衣柜花纹都清楚 |
| 外置 USB | 56 | 整体朦胧，亮处有光晕 |

外置摄像头常见的三个物理原因，按概率排：

1. **镜头保护膜没撕**（新摄像头几乎都有，观感就是"朦胧 + 光晕"）；
2. **镜头有指纹/灰**，用眼镜布擦；
3. **定焦镜头跑焦**——不少廉价摄像头镜头筒可以拧（对焦环），对着 40~50cm 处的手拧到最清晰。

先在 Windows「相机」应用里看一眼：如果那里同样糊，就与程序无关。

> 模糊会直接拉低关键点精度（抖动变大、捏合比噪声变大），所以**这一项值得较真**。
> 如果外置怎么调都糊，用回内置摄像头也是合理选择——代价是画面暗一些（实测亮度 81 vs 147）。
