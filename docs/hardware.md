# 硬件与摄像头适配指南

> 一句话结论：**任何能输出 640×480 的摄像头都能跑**。宽高比不是 4:3 也
> 不用改阈值（程序会自动补偿）；分辨率更高**不会更准**，只会更吃 CPU。

本文回答三件事：

1. 我的摄像头能不能用；
2. 不能用的症状长什么样，怎么定位；
3. 换了摄像头之后，哪些配置**必须**改、哪些**不用**改。

---

## 1. 最低要求与推荐配置

| 项目 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| 摄像头 | 320×240 @ 15fps | **640×480 @ 30fps** | 720p/1080p 也行，但没收益（见 §3） |
| 接口 | USB 2.0 | USB 3.0 | USB 2.0 带宽跑不动 720p 的未压缩流 |
| 系统 | Windows 10 / 11 | Windows 11 | 非 Windows 只能 `--safe-mode`（不注入输入） |
| Python | 3.10 | 3.12 | 用了 `X \| None` 与 `slots=True` |
| CPU | 4 核 | 6 核以上 | MediaPipe 单帧推理 ~30ms |
| 内存 | 4 GB | 8 GB 以上 | 常驻约 400 MB |
| 显卡 | 不需要 | — | MediaPipe 走 CPU |

摄像头**不需要**深度、不需要红外、不需要自动对焦。单目彩色即可。

## 2. 先跑体检脚本（不要猜）

```bat
python scripts\probe_camera.py
```

（在你自己的项目目录下，直接 `python scripts\probe_camera.py` 也可以。别忘了一次摄像头权限确认：
设置 → 隐私和安全性 → 摄像头 → 允许桌面应用访问。）

它会打印一张表，说明**你要的每个分辨率，驱动实际给了多少**：

```
    请求分辨率      驱动返回      状态
    ------------    ------------  --------------------
       320×240         320×240      原生
       640×480         640×480      原生
       800×600         640×480      静默改成 640×480
      1024×768        1280×720      静默改成 1280×720
      1280×720        1280×720      原生
      1920×1080       1280×720      静默改成 1280×720

    原生档位：320×240, 640×480, 1280×720
    实际画面：640×480  （宽高比 1.333，4:3）
    实测帧率：30.2 fps
    MJPG：YUY2
```

这张表是上面那台机器（作者本人的笔记本内置摄像头）在 **dshow** 下的真实输出。
⚠️ **帧率那一行别当固定值**：同一只摄像头换 `msmf` 会变成 30fps（见 §5.1），
换后端/换时间都要重跑一次。它说明的是另外三件事：

- **只有三个原生档位**：320×240 / 640×480 / 1280×720。想要 1080p？驱动会把
  你静默降级回 720p，`set()` 照样返回成功——不读回实际值就永远发现不了。
- **MJPG 协商不下来**（拿到 `YUY2` 未压缩流）→ USB 2.0 带宽被吃满 →
  1280×720 在这个后端上只有 **10fps**，640×480 才有 30fps。
- **宽高比是 4:3**，正好是项目的标定基准，什么都不用调。

把这段输出贴进 issue，任何人一眼就能判断你的硬件处在什么档位。

## 3. 为什么"更高分辨率"不是升级

MediaPipe 会把手部图解算到**固定输入尺寸**再送进网络。你给 640×480 还是
1920×1080，送进模型的东西几乎一样，所以：

| 换成 720p / 1080p 能得到 | 得不到 |
|---|---|
| 左右视野更宽（手可以在更大范围里晃） | ❌ 更高的识别精度 |
| 给 `recognition_zoom` 留更多像素余量 | ❌ 更稳的关键点坐标 |
| — | ❌ 更高的帧率（反而可能更低） |

所以**默认配置就是 640×480 @ 30fps**，这是刻意选的，不是偷懒。
只有当你的手经常移出画面、必须靠更宽的视野时，才考虑升到 720p，并且要接受
帧率可能掉到 10fps（USB 2.0）或者必须换 USB 3.0 接口。

---

## 4. 宽高比：程序会自动补偿，但你需要知道原理

归一化坐标里 **x 除以画面宽、y 除以画面高**，两个方向的比例不同。于是：

- 掌宽（`5 → 17`）是**纯横向**的线段；
- 捏合比（`拇指尖 4 → 食指尖 8`）是**斜向**的。

画面从 4:3 变到 16:9 时，横向长度在归一化坐标里被多压 25%，而纵向不受影响，
所以**捏合比会整体漂移**。作者在姿态库上实测（4:3 → 16:9，同一姿势）：

| 姿势 | 4:3 捏合比 | 16:9 不补偿 | 漂移 |
|---|---|---|---|
| 五指张开（进入门） | 1.279 | 1.682 | **+31.5%** |
| 张开→右捏合 | 0.593 | 0.728 | **+22.8%** |
| 侧掌 | 8.559 | 10.193 | **+19.1%** |
| 正常指向 | 1.346 | 1.669 | **+23.9%** |

`pinch_engage` 默认 0.42、`pinch_release` 默认 0.55 —— 漂 +23% 意味着
**捏到一半就触发、松开时却松不掉**。这就是"换台电脑就不好用"的真正原因。

**现在的做法**：`CameraWorker` 把画面宽高比随每帧一起传给手势引擎
（`HandObservation.image_aspect`），引擎把横向长度乘上
`宽高比 ÷ (4/3)` 还原到标定尺度：

- 4:3（1.333）→ 倍率 **1.000**，与历史行为**完全一致**，所有阈值原封不动；
- 16:9（1.778）→ 倍率 **1.333**，把那 25% 的缩水补回来；
- 上表四种姿势补偿后的漂移均为 **+0.0%**。

所以：**换摄像头不需要重标捏合阈值。** 但手感和作者的机器一定还有差别，
微调方向见 [`tuning.md`](tuning.md)。

## 5. 换摄像头时的检查清单

1. `probe_camera.py` 确认原生档位、宽高比、MJPG、实测帧率；
2. 若原生有 640×480 → **配置保持默认**，什么都不用改；
3. 若**只有** 16:9 档（很多 720p 网络摄像头属于此类）→
   配置可以写 1280×720，程序会自动补偿宽高比；
   但若实测帧率 < 20fps，改回 640×480（多数摄像头在 4:3 下能跑满 30fps）；
4. 若帧率上不去 → **先换采集后端**（见 §5.1），再考虑换 USB 口；
5. 若画面偏暗（< 55 亮度）→ 程序会自动提亮，无需改配置；
6. 换完跑一次 `python -m handmouse --safe-mode --diagnostic-seconds 20`，
   看 `hand_detection_rate` 是否 > 0.9。

### 5.1 采集后端：帧率不够时第一个该试的开关

`config.json` 里的 `camera_backend`，三个取值：

| 值 | 含义 | 什么时候用 |
|---|---|---|
| `"dshow"` | DirectShow（**默认**） | 兼容性最好，先试它 |
| `"msmf"` | Media Foundation | dshow 下帧率明显偏低时 |
| `"any"` | 让 OpenCV 自己挑 | 排查问题 |

**这不是自动探测**——同一条命令两次启动必须走同一条路径，否则"这次好使下次
不好使"根本没法复现。所以由你显式指定，程序在启动日志里把实际后端打出来：

```
摄像头 1 实际输出 640×480 @ 30.0fps（配置 640×480@30fps，宽高比 1.333，后端 msmf）
```

实测（2026-10-25，作者机器插了外置摄像头之后，**每次重开进程测**）：

| 摄像头 | dshow | msmf |
|---|---|---|
| 笔记本内置（ID 0） | 10.0 fps | **29.9 fps** |
| 外置 USB（ID 1，640×480 上限） | **10.0 fps（锁死）** | **29.8~30.4 fps** |

两只摄像头都是 **msmf 才有 30fps**。外置摄像头在 dshow 下是**锁死的 10fps** ——
换成 320×240、160×120 也一样是 10.0，说明不是带宽问题，而是 dshow 路径下的
自动曝光把一帧的曝光时间拉到了 1/10 秒。

**为什么不能自己调曝光**：这台摄像头在 dshow 下 `CAP_PROP_EXPOSURE` /
`CAP_PROP_AUTO_EXPOSURE` / `GAIN` / `FOCUS` 的 `set()` **全部返回 False**、读回 −1，
只有 `BRIGHTNESS` / `CONTRAST` 能改（改了也只改数字亮度，不改帧率）。
所以帧率这一项**只能靠换后端**解决，没有第三种办法。

⚠️ 反过来说：MSMF 在部分摄像头/驱动上是坏的（打不开、出黑帧、或画面异常）。
这也是 `dshow` 一直被当默认、`camera_backend` 默认值也写成 `dshow` 的原因。
**换过摄像头之后再跑一次 `probe_camera.py` 对比两个后端的实测帧率**，别凭感觉。

### 5.2 刚启动的一两秒画面发白，是正常的

自动曝光在打开后会先大幅摆动再稳定。实测同一只摄像头，打开后第一个 0.5 秒内
抓到的帧亮度可以到 **243（近乎全白）**，充分预热 2 秒后同一场景只有 **77~97**。

所以：

- 看到预览窗刚出来那一下发白 **不是故障**，等两秒；
- 但如果**两秒后还是白的**，那才是真过曝 —— 换后端（见 §5.1）；
- `probe_camera.py` 的 `实际画面` 亮度是预热后测的，可以直接当结论用。

### 5.3 画面发虚：基本是硬件，不是软件

见 [`troubleshooting.md`](troubleshooting.md)「画面发虚」一节。一句话结论：
两个后端一样虚、分辨率降到 320×240 也一样虚 → 是镜头光学问题（保护膜 / 脏 / 跑焦），
软件改不动。

## 6. 多摄像头 / 外接摄像头

```bat
python -m handmouse --camera 1          :: 用 1 号摄像头（笔记本内置通常是 0）
```

序号按 Windows 的枚举顺序，不稳。**用哪个口插就先试 0、1、2**，或者打开
"相机"应用确认当前是哪一个。选定后写进 `config.json` 的 `camera_index`，
以后双击启动就用它。

USB 摄像头**插拔后序号可能变**。拔了再插如果识别不到，跑一次体检脚本看还有没有。

## 7. 已知的硬件坑（都实测过）

| 现象 | 真因 | 处置 |
|---|---|---|
| 1280×720 只有 10fps，640×480 有 30fps | 摄像头只吐 YUY2 未压缩流，USB 2.0 带宽吃满 | 用 640×480，或换 USB 3.0 |
| 请求 1080p，实际 720p | 驱动静默降级 | 程序现在会读回实际值并打印 warning，不会再"假装成功" |
| 请求 1024×768，拿到 1280×720 | 驱动只认标准档位 | 用原生档位，别用中间值 |
| 画面亮度 143、标准差 44（正常） | — | 说明曝光没问题；若亮度 < 30 会自动 CLAHE 增强 |
| 手在画面边缘时捏合失灵 | 手被画框切掉，二维几何不可信 | 这是**故意**的：指尖出框时不做锚定（见 `gestures.py`） |
| 摄像头被别的软件占用 | 会议软件 / 相机应用没关 | 关掉占用方；程序会提示"无法打开摄像头" |

## 8. 想验证「是不是硬件的问题」

三个层次，从便宜到贵：

```bat
:: 1) 摄像头本身能吐什么
python scripts\probe_camera.py

:: 2) 采集 + 推理能不能跑到 30fps（不注入鼠标）
python -m handmouse --safe-mode --diagnostic-seconds 20

:: 3) 端到端（注入鼠标，务必先把手离开画面再退出）
python -m handmouse
```

`safe-mode` 下如果检测率也上不去，问题在摄像头/光照/模型，不在手势逻辑 ——
这样可以省掉一大圈瞎调参数。
